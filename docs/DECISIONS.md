# Registro delle decisioni

Decisioni prese in autonomia (brief §1). Formato: ID, decisione, motivo. Le modifiche agli schemi dati vanno sempre registrate qui.

| ID | Decisione | Motivo |
|---|---|---|
| D-001 | Collezioni definite in `src/content.config.ts` con loader `glob`; i dati restano in `src/content/<collezione>/` (JSON per aziende/eventi/prompt, Markdown per articoli). | Astro 7 non supporta più il vecchio `src/content/config.ts`. Il contratto è lo stesso richiesto dal brief. |
| D-002 | Un solo interruttore `PUBLIC_SITE_MODE=beta\|production` (default `beta`) governa robots meta, `robots.txt`, sitemap. Il dominio sta in `PUBLIC_SITE_URL` / `site` di `astro.config.mjs`. | Brief §3.5 e §4: il passaggio a production deve essere una sola modifica. |
| D-003 | CSS con design tokens (custom properties) e stili scoped dei componenti, niente Tailwind. | CSS più piccolo e prevedibile per il budget di 20 KB; i token servono anche ai riempimenti SVG della mappa e al dark mode. |
| D-004 | Font di sistema: serif di sistema per i titoli, sans di sistema per il testo. Nessun webfont. | Zero byte di font, zero CLS, nessuna richiesta bloccante: è l'alternativa ammessa dal brief §4.1. L'identità passa da palette, titoli serif e layout. |
| D-005 | Isole interattive in TypeScript vanilla (script dei componenti Astro, caricati come moduli con `IntersectionObserver` o a interazione). Preact è installato ma va usato solo se un'isola lo giustifica, con motivo scritto qui. | Brief §4.1: JS minimo. Un filtro di lista non richiede un runtime UI. |
| D-006 | Mappe: anteprima SVG statica delle 9 province (link/filtri, nessun JS) + Leaflet e tile OSM caricati solo al clic su "Apri mappa interattiva" o all'ingresso nel viewport. Tile standard `tile.openstreetmap.org` con attribuzione. | Lighthouse 100 e brief §4.1. Le tile OSM vanno bene per il traffico di una beta; con traffico reale si valuta un provider dedicato (vedi policy OSM). |
| D-007 | Lighthouse CI gira su una build locale con `PUBLIC_SITE_MODE=production`. | In beta il `noindex` fa fallire per scelta l'audit SEO "is-crawlable". Il resto della pagina è identico, quindi la misura vale per entrambe le modalità. |
| D-008 | CSP generata da Astro (`security.csp`, meta con hash degli script inline) + header di sicurezza in `public/_headers` (HSTS, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, `frame-ancestors`). | Best Practices al 100 senza `unsafe-inline` per gli script. |
| D-009 | Pagine aggiunte all'albero del brief §5: `/contatti/` (citata al §2), `/cerca/` (destinazione della `SearchAction`, `noindex` anche in production), `/404`. | Coerenza con §2 e §9.2. |
| D-010 | Fixture fittizie in `src/fixtures/`, caricate solo con `USE_FIXTURES=1`. Slug con prefisso `esempio-`, nomi `[FITTIZIO]`, domini `.example`. `npm run validate` blocca se ne trova in `src/content/`. | Brief §3.1. |
| D-011 | Campi aggiunti agli schemi del brief §6: aziende `geo_precision`, `same_as`; eventi `status`, `end_time`, `venue_address`, `organizer_url`; articoli `seo_title`, `answer`, `order`, `reviewed_at`, `related_prompts`; prompt `tested_at`, `test_notes`. Vocabolari controllati in `src/lib/taxonomies.ts`. | Servono a JSON-LD onesto (geo solo se preciso), paragrafo di risposta diretta, "articolo successivo", tracciabilità del test dei prompt, entità scritte sempre allo stesso modo. |
| D-012 | Articoli YMYL: con `needs_human_review: true` sono esclusi dalla build. Per approvarli: `needs_human_review: false` + `reviewed_at`. | Brief §3.8 e DoD. |
| D-013 | "Prossimi" e "archivio" eventi si calcolano alla data di build (fuso Europe/Rome). Serve una ricostruzione periodica (workflow giornaliero predisposto, disattivato). | Sito statico. |
| D-014 | Liste (directory, province, archivio): tutte le schede nell'HTML finché sono ≤ 100; sopra quella soglia paginazione statica da 48 (`/…/pagina/2/`). I filtri lavorano in JS sulle schede presenti nella pagina; lo stato dei filtri sta nell'hash dell'URL. | Con 30–100 record l'HTML resta leggero e i filtri non richiedono fetch. |
| D-015 | Form (Segnala, Rimozione, Contatti): `<form method="post">` HTML nativo verso l'endpoint in `PUBLIC_FORM_*_URL` (compatibile con Formspree). Se l'URL manca, il form è disattivato con avviso chiaro. | Zero JS, nessuno script di terze parti. Tally richiederebbe un embed. |
| D-016 | Immagini Open Graph 1200×630 generate in build (satori + resvg, font OFL incluso nel repo solo per l'immagine). | Brief §9.1: un'immagine per pagina, nessun servizio esterno. |
| D-017 | Coordinate aziende: geocoding Nominatim dall'indirizzo pubblico (`geo_precision: "indirizzo"`) oppure centro del comune (`"città"`). `geo` e `address` in JSON-LD solo con precisione "indirizzo". | Brief §9.2: "solo se verificati". |
| D-018 | Orchestrazione: gli agenti in `.claude/agents/*.md` (model: sonnet) sono la definizione ufficiale. In questa sessione l'orchestratore li lancia come subagenti Sonnet che leggono quel file e la loro spec, perché le definizioni create a sessione avviata vengono caricate solo dalla sessione successiva. | Nessun effetto sul risultato; i file restano per le sessioni future e per le pipeline. |
| D-019 | Nei testi si parla di "province" (lessico comune). La pagina metodologia spiega che dal 2015 sono liberi consorzi comunali e città metropolitane. | Chiarezza per il pubblico. |
| D-020 | Tool degli agenti leggermente estesi rispetto alla tabella del brief §11: `Bash` a ricercatori (script di geocoding), copy-editor e prompt-librarian (per `npm run validate`); `Write` al qa-factchecker (solo `docs/qa/`); `Glob`/`Grep` a tutti per leggere senza sprechi. | Ogni spec richiede di eseguire la validazione prima del report. |
| D-021 | Deploy della beta via GitHub Actions + wrangler (`pages deploy`) su push a `main`, con i secret `CLOUDFLARE_API_TOKEN` e `CLOUDFLARE_ACCOUNT_ID` impostati dall'utente. Progetto Pages `aisicilia`. | Scelta dell'utente (secret già configurati su GitHub). |
| D-022 | Sito solo in italiano (indicazione esplicita dell'utente). Nessuna traduzione né versione linguistica; `hreflang` presente solo come codice disattivato. I contenuti che insegnano a usare l'AI per tradurre i testi delle imprese restano (caso d'uso del brief §7.3–7.4). | Richiesta dell'utente, brief §15. |
| D-023 | I link Markdown verso articoli non ancora pubblicati (YMYL in revisione) vengono resi come testo semplice da un plugin remark (`src/lib/markdown/remark-unpublished-links.mjs`). All'approvazione tornano link senza modifiche ai testi. | Niente link rotti né pagine orfane mentre gli articoli 6 e 10 attendono la revisione. |
| D-024 | Design v2 "Basalto e maiolica digitale" (`docs/specs/design-v2.md`): palette pietra lavica / calce / blu maiolica / terracotta / pistacchio / ocra, niente viola; font self-hosted Familjen Grotesk (variabile, ~19 KB) + IBM Plex Mono 500 (~15 KB) per i dati. Sostituisce D-004 (font di sistema). | Richiesta dell'utente: identità distintiva, siciliana e tech, non generica. Il peso dei font (~34 KB, preload del solo Familjen, fallback con metriche regolate) è compatibile con Lighthouse 100. |
| D-025 | RankWit inclusa nella directory e **in evidenza** (prima posizione nell'elenco regionale e in quello della provincia di Catania), per decisione esplicita dell'utente. Nuovi campi `featured` e `disclosure` nello schema aziende: le schede in evidenza mostrano l'etichetta "In evidenza" e la nota di trasparenza sul rapporto con l'autore; la metodologia spiega il criterio. Fonte di verifica: sito ufficiale + registro startup innovative (sede Aci Castello, CT). | Decisione editoriale dell'utente; la nota di trasparenza mantiene credibile la directory rispetto ai criteri dichiarati in /metodologia/. |
